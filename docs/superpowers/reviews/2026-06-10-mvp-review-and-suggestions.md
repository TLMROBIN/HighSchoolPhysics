# MVP 审核报告与优化建议（2026-06-10）

> 审核范围：`highschoolphysics/` 全部源码（约 5300 行）、`tests/`（18 个测试，当前全部通过）、
> `docs/superpowers/specs` 蓝图与 `plans` 两份计划文档。
> 本文档只记录建议，不包含已执行的改动。

## 总体评价

方案文档质量很高：蓝图有明确的 MVP 切线、快照/版本化思路、隐私与权限要求；feedback 计划把 2B–2G 阶段拆分得清晰且各带验收标准。代码与文档声明基本一致：Phase 1 + 2A 声称的能力（本地账号、测评闭环、LLM 候选审核、错题导出、管理员本体 CRUD、审计）确实都有实现和测试覆盖。

主要差距集中在两类：
1. **权限模型只做了一半**：`AuthService.can()` 实现了"主体-资源-操作"检查并有测试，但 HTTP 层完全没有接入它，导致存在真实的越权漏洞（见 C1）。
2. **教学闭环的"环"还没闭上**：错题→重做→掌握更新这条核心链路只有数据字段，没有流转逻辑；教师审核标签时不能编辑选择；错因只有一个写死的字符串。这些直接影响诊断数据的可信度，也就是教学价值。

## 一、代码实现问题（按严重程度排序）

### C1.【高·越权】错题本导出端点对所有登录用户开放

`server.py:804-821`：`/export/wrong-book/<assessment_id>` 只检查 `if not user`，**学生登录后可以导出任意测评的全班错题本**，看到其他同学的姓名、学号、原始作答和掌握标记。蓝图明确要求"学生只能查看自己的错题"。

建议：
- 学生角色：强制 `student_id = user["id"]`，且忽略 `class_id` 参数。
- 教师角色：调用 `AuthService.can(user, "export", "assessment", assessment_id)` 校验任教班级。
- 补一条 HTTP 层测试：学生请求他人 `student_id` 时应 403。

### C2.【高·架构】`AuthService.can()` 从未被 server 调用

`auth.py:78-100` 的权限矩阵有实现、有测试（`test_security_auth.py:30`），但 `server.py` 的所有路由只判断 `user["role"]`。教师侧 `grade`、`resolve-review`、`approve-candidate` 都没有班级范围校验——当前单教师单班级演示数据下暴露不出来，一旦 Phase 2D 引入多班级就是真实漏洞。

建议：在 `do_POST`/`do_GET` 各业务分支接入 `can()`；并在 demo seed 中**加入第二个班级和第二位教师**，让权限边界在 UI 和测试里被真正行使（现在 `test_security_auth` 是临时 insert 一个班级才测得到）。

### C3.【高·正确性】重新批改会静默清空学生掌握标记

`repository.py:803-812`（`grade_assessment`）：每次批改先 `delete from mastery_marks ... delete from wrong_questions` 再重建。学生标记的"基本掌握"等记录在教师重新点一次"批改并发布"后全部丢失。`test_regrading_after_wrong_question_mastery_does_not_violate_foreign_keys` 只验证了不报错，恰好掩盖了数据丢失。

同时这违反蓝图自己的约束："已发布或已归档的测评批次不能静默修改；若需要修正，必须产生改分或修订记录。"

建议：
- 已发布的测评再次批改时，要么拒绝并要求显式"修订"操作，要么 upsert 错题记录（保留 id 不变，掌握标记自然保留），并写入改分审计。
- 把上述测试改成断言"重批后掌握标记仍在"。

### C4.【中·正确性】候选标签审核：教师无法编辑，服务端硬编码截断

`server.py:854-865`：approve 时取 `knowledge_tags[:1]`、`ability_tags[:2]`，教师在 UI 上只有一个"确认"按钮，不能增删改标签。蓝图要求审核界面支持"一键确认/编辑/删除"；feedback 计划 2C 要求"每个标签族最多 3 个正式标签，教师可编辑/删除/替换"。错误标签会直接污染班级诊断和后续掌握度统计——这是教学价值链上的关键质量闸门。

另外此处直接调用了 `repo._candidate_payload()` 私有方法并手写 SQL，candidate_id 不存在时会抛未捕获异常（见 C5）。建议在 repository 增加 `get_candidate(candidate_id)` 公开方法，UI 上给候选标签加复选框，approve 接口接收教师勾选后的 id 列表。

### C5.【中·健壮性】POST 处理无统一异常处理

`do_POST` 中 `payload["candidate_id"]`、`payload["node_id"]` 等直接下标访问，缺字段抛 KeyError；repository 抛 ValueError（如节点不存在）也没人接。结果是连接中断/500 无响应体，前端只显示 "request_failed"。

建议：在 `do_POST` 外层包一个 try/except，把 `ValueError`/`KeyError` 转成 400 JSON `{"error": "..."}`，其余异常转 500 并记录日志。前端 `setStatus` 已能展示 error 消息，收益立竿见影。

### C6.【中·安全】`must_change_password` 字段存在但登录流程不执行

蓝图与 README 都承诺"临时密码 + 首次登录强制修改"，`import_student` 也写入了 `must_change_password=1`，但 `auth.py:25-47` 的 `login()` 完全忽略该字段，系统里也没有改密码接口。建议：登录后检测该标志并跳转强制改密页；顺带补"教师重置本班学生密码"接口（蓝图承诺，当前缺失）。

### C7.【中·并发】SQLite 未开 WAL / busy_timeout

`db.py:11-18`：`ThreadingHTTPServer` 多线程 + 每请求新建连接，默认 journal 模式下并发写会抛 `database is locked`。平板班级场景（40 人同时标记掌握）很容易触发。建议 `connect()` 中加 `pragma journal_mode=WAL` 和 `pragma busy_timeout=3000`。

### C8.【低·正确性】学生端"待重做"标签页是错题本的完整复制

`server.py:359`：`redo_cards=wrong_cards`。repository 明明算好了 `redo_queue`（`repository.py:1217`）却没有被渲染使用；且同一批卡片带相同 `id="question-..."` 渲染两次，HTML id 重复导致锚点跳转失效。建议待重做 tab 改用 `dashboard["redo_queue"]` 渲染，卡片 id 加 tab 前缀。

### C9.【低·噪音】审计日志被页面浏览刷屏

`class_diagnostics()` 每次调用写一条 `class_diagnostics_viewed` 审计，而教师仪表盘每次刷新都会调用它（前端每次操作后还自动 reload）。审计日志会迅速被浏览事件淹没，反而掩盖关键操作。建议：浏览类事件不写审计，或单独分表/分级；审计保留给变更类操作。

### C10.【低·性能】知识树构建存在 N+1 与重复查询

- `student_knowledge_tree` 对每个节点调 `related_questions_for_knowledge`，后者每次又调 `descendant_knowledge_ids` → `knowledge_nodes()` 全表查询：节点数 N 时是 O(N²) 次查询。Phase 2B 导入真实教材目录（数百节点）后学生首页会明显变慢。
- `student_dashboard` 调 `list_wrong_questions_for_student` 两次（一次自己用、一次在 `mastery_counts` 里），每条错题又单独查一次 tags。

建议：一次性取全部节点建内存索引、一次 join 取全部 question_tags 再分组，把复杂度降到 O(N)。

### C11.【低·演示残留】教师仪表盘硬编码 `assess-week-1`

`repository.py:1186`：`teacher_dashboard` 写死 assessment_id，UI 也只渲染 `assessments[0]`。多测评批次时复核列表和诊断永远指向 demo 数据。Phase 2D 之前需要改成"按教师任教班级列出测评 + 选中查看"。

### C12.【低·安全备忘】其余记录在案的弱点

- `security.py:78` 的 XOR `protect_secret` 自己也注明不是真加密——接入真实 LLM Key（2C）前必须换成 `cryptography.Fernet` 或系统 keyring。
- 登录无失败次数限制/锁定（有审计无动作）；局域网部署风险可控，但共享平板上值得加每账号节流。
- `datetime.utcnow()` 在 Python 3.12+ 已 deprecated，建议换 `datetime.now(timezone.utc)`。
- 登录页内嵌演示账号密码，正式部署前需移除（建议挂在 `--demo` 启动开关下）。

### C13.【低·测试缺口】没有 HTTP 层集成测试

现有测试都直接调 repository/render 函数，`PhysicsHandler` 的路由、鉴权、payload 解析零覆盖——C1 的越权正是这层的洞。建议加一组用 `http.client` 对 `ThreadingHTTPServer` 实测的用例：登录→cookie→越权访问 403→学生导出他人数据 403→缺字段 POST 返回 400。

## 二、功能改进建议（目标：提升教学效果）

### T1. 闭合"错题→重做→掌握"循环（最高优先级）

这是系统的核心教学主张，目前只有静态展示：`redo_status` 永远是 `pending`，没有任何代码会流转它；学生重做无入口、无记录。掌握标记纯靠学生自觉点按钮，与作答证据脱节。

建议最小闭环（可在 2D 之前先做）：
- 学生在错题卡上点"重做"，进入只显示题干/选项的作答态，提交后即时判分（判分引擎已有）。
- 重做正确 → `redo_status='done'`，并提示学生更新掌握标记；重做错误 → 保留在待重做并记录次数。
- 重做记录写入独立表（蓝图本就定义了"重做记录对比"），错题卡上展示"原答 D → 重做 ✓"。

理由：没有重做证据，掌握标记和后续 2E 的阈值统计都是空中楼阁；这一步还能直接给 2E 提供"正确/错误计数"数据源。

### T2. 错因维度：从写死字符串到教师可标注

`grade_assessment` 给所有错题写同一句 `"客观题自动批改未得分"`。蓝图的标签体系里错因标签（概念混淆/受力遗漏/计算失误/审题偏差…）是与知识点并列的一等公民，而错因恰恰是教师讲评时最关心的维度——"哪个知识点错"回答考什么，"为什么错"才回答怎么教。

建议：
- 建错因标签字典（管理员维护，随本体版本化）。
- 教师在复核/批改后界面上可为高频错题快速勾选错因（可批量：同题同错因一键应用）。
- 班级诊断增加按错因聚合的视图。

### T3. 诊断指标修正：错误率口径与空白卷区分

`class_diagnostics` 的 `error_rate = wrong_count / participants` 有两个问题：
- **分母错位**：知识点/能力标签各自关联的题数不同。某标签关联 3 题、每题 1 人错 → 错误率 100%，而单题标签 1 人错 → 33%，教师会误读。正确口径应是"该标签下错误人次 / 该标签下作答人次"。
- **空白≠做错**：seed 数据里 stu-1003 的 q-fill-1 是空字符串，被一律计入"错"，没有缺考/空白标识。讲评时"不会做"和"没做"是完全不同的教学信号。

建议：错误率改用 attempts 作分母；`student_responses` 空答案单独标记 `blank`，诊断中分列"错误/空白"。

### T4. 教师审核体验：标签编辑 + 待审核队列（与 C4 同源）

除了能勾选，建议把审核界面做成 2C 验收要求的形态：每个标签族（知识/能力，将来加素养）并排显示候选、置信度、依据，支持替换为字典中其他标签、每族上限 3 个。审核效率决定了教师是否愿意持续供给高质量标注——这是整个数据飞轮的进料口。

### T5. 错题本导出：覆盖蓝图承诺的教学场景

当前导出格式固定（无答案无解析、按学生分页）。蓝图列了明确的场景矩阵：只题目 / 题目+答案 / 题目+解析、按知识点分组、合并重复错题、附答案页。建议至少先加两项性价比最高的：
- "附答案解析页"开关（学生练完自查，家长辅导也用得上）；
- 按知识点分组模式（适合考前专题复习，与图谱主张呼应）。
导出表单已有筛选骨架，加 checkbox 改 `build_wrong_book_html` 参数即可。

### T6. 学生端图谱：让掌握状态可视化先行

学生图谱节点目前只在 `<title>` 悬浮提示里带掌握状态，平板上无 hover。2E 计划了四档颜色，但现在就可以用已有的手动标记给节点上色（未标记=灰、未掌握=红、基本掌握=黄、已掌握=绿、需教师讲解=醒目标识）——改动小，"一眼看到自己哪里薄弱"正是图谱优先首页的卖点。

注意 `_render_student_relation_graph` 的节点坐标写死了 5 个 demo id（`server.py:168-174`），2B 导入真实教材目录后所有新节点会叠在 fallback 位置。建议届时换成简单的分层布局（按 level 分列、同级均匀分布），不必等 Phase 3 的完整交互图谱。

### T7. 演示数据加入"对照组"

当前 seed 只有 1 班 3 学生 1 教师，导致：年级平均=本班平均（教师页那行说明形同虚设）、跨班权限无从演示、诊断没有分布感。建议 seed 增加高二(2)班 + 第二位教师 + 若干学生与作答，让"本班 vs 年级"对比、权限隔离、教师筛选都有真实数据可看——给老师演示时说服力完全不同。

### T8. 下一阶段排序建议：2B → 2C → 2D

计划文档把选择权留给用户，这里给出推荐及理由：
- **先 2B（默认教材知识体系）**：标签质量是诊断价值的地基；且 2B 纯数据工作、风险低，完成后 T6/T7 立刻受益。
- **再 2C（真实题库+文档解析）**：有了可靠的知识树，LLM 候选标注才有靠谱的候选空间；MarkItDown/MinerU 集成工作量大但可增量交付。
- **后 2D（答题卡 OCR）**：技术风险最高（PaddleOCR 识别率、身份绑定），等题库和标签稳定后再上，失败成本最低。
- 穿插建议：T1（重做闭环）和 C1-C3（安全/数据修复）不依赖任何阶段，建议作为 2B 并行的小步快跑项。
